# experiment-record（実験の記録）

実験の結果は、後から経緯を追え、別の人が同じ条件で再実行できる形でリポジトリに残します。PR 本文や VM 上のファイルだけに残しません。

## 手順

1. 計画: `references/record-template.md` を `docs/experiments/YYYY-MM-DD-<short>.md` に写し、目的、仮説、変える条件と変えない条件、採否の基準、繰り返しの回数を先に書きます。S 番号がある実験は名前にも付けます。採否の基準は数値で決め、結果を見てから変えません。繰り返しは 5 回以上を基本とし、中央値と最小・最大を出します。構築可否など 1 回で確かめる試験は、回数と理由を書き、性能の結論に転用しません。
2. 基準の固定: 基準の commit、ホストの OS、QEMU・Buildroot・GCC・カーネルの版、出力先のパス（`O=`）、使い回した出力の状態（`*-reconfigure` の有無、ccache 統計、ビルドツリーが cold か warm か）を書きます。A/B 比較は両側を同じ warm/cold 状態で測り、違うときは記録に明記します（`kernel-variant-sweep.sh` は実行ごとに `<CSV>.meta` sidecar にこれらを書きます）。ツールの版は、実際に使われたバイナリから取ります（例: genimage が使う `output/host/sbin/mke2fs -V`）。QEMU などのツールを開発用イメージに入れて使うときは、binary の SHA-256 と、それを作った commit または image の層を書きます。`run-qemu.sh` がログに出す `run-qemu: sha256` の行を記録に写します。
3. 計測器の検証: 本番の前に、計測器が正しく反応するかを確かめます。既知の負荷を与える、アイドル時の増分が 0 かを見る、同じ条件で 2 回測って差を見る（A/A 試行）、のいずれかを行い、結果を記録します。
4. 実行: 実行に使うスクリプトとフックは `board/cardputerzero/tools/bench/` などリポジトリ内に置きます。通常のイメージには入れず、ローカルの測定時にだけ有効にします。重い実験は CI に載せません。コマンドと環境変数は、記録にそのまま書きます。runner は、条件の選択を CLI 引数で受け取ります（`docker/msd-dev` は決まった環境変数しか渡しません）。既存のログの置き場所や CSV があれば、上書きせずに止めます。
5. 記録: 人が読む要約は Markdown に、生の値は同じ名前の `.csv` に書きます（列は `assets/results-template.csv`）。捨てた試行も理由と一緒に残します。大きなログはコミットせず、再生成の方法と SHA-256 を書きます。CSV は 1 ファイル 1 MB までを目安にします。
6. 反映: `docs/experiments/README.md` の一覧に 1 行足し、結論を該当する調査文書に反映します。S 番号がある実験は docs/research/verification/experiment-catalog.md の対応する行も更新します。以前の記述を正すときは `docs/research/corrections.md` にも書きます。PR 本文には記録へのリンクを書きます。日本語の文章は yomiyasu の lint を通します。

## 集計と証拠の保存

- CSV は結果・終了状態を含む全列を読み、初回起動、通常起動、失敗、欠損を分けます。失敗行を消したり、その数値を成功した試行の中央値に混ぜたりしません。非有限値、重複 run ID、不足した反復数も検査します。
- 同じ入力の A/A と、失敗させる負の対照で runner と集計器を試します。ログに成功の目印があっても、後の異常終了を見落とさないようにします。
- 実行中のスクリプトは編集しません。修正は別の写しで試すか、実行の終了を待ちます。再試行は新しい run ID と出力先を使います。
- 作業ツリーや出力先を消す前に、生ログ・入力 hash・メタデータを永続的な保管先へコピーし、ファイル数と SHA-256 を照合します。参照先と取得方法を記録し、コピーを確認するまで元を消しません。
- ログがない場合、本文・CSVの再集計と生ログの再確認を区別します。既存の SHA-256 だけでログを読んだとは書きません。新しい試行は過去の試行と別の記録にします。
- 差が採否の閾値を超えなかったことは、統計的同等性や、別の機材で差がないことの証明ではありません。

## 提出前の確認

- [ ] 採否の基準を、結果を見る前に書いた
- [ ] 版は、実際に使われたバイナリから取った
- [ ] 計測器の検証を行い、値が 0 や全条件で同じになっていないか確かめた
- [ ] 測った binary（QEMU、kernel、image）の SHA-256 が、記録した commit から作ったものと一致する
- [ ] 計測系の比較で ccache・ビルドツリーの warm/cold を条件欄に書いた（混在させていない）
- [ ] 試験が対象の機能を実際に動かしている（ログで確かめた）
- [ ] 判定に使う行や marker が、負の対照（機能を止めた回）では出ないことを確かめた
- [ ] 実行ログのエラーと警告を読んだ（成功の判定だけで済ませていない）
- [ ] 改善だけでなく、劣化しうる指標も測った
- [ ] 絶対値を書いた（相対値だけにしていない）
- [ ] QEMU での値は、実機の値ではないと明記した
- [ ] 失敗・中止した試行と、その理由を残した
- [ ] 根拠に VM や個人環境のパスを書いていない
- [ ] 一覧、調査文書、S 表、必要なら corrections.md を更新した

落とし穴の実例と根拠は `references/pitfalls.md` にあります。

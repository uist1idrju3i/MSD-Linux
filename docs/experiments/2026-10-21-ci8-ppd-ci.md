## 目的と仮説

PR #78 の run（build job 118971806540）では、ccache の hit 率が 99.89 % でも、Buildroot の step に 1,235 秒かかりました。Buildroot の top-level `Makefile` は、`BR2_PER_PACKAGE_DIRECTORIES` が無効だと `.NOTPARALLEL` を付けます。そのため CI の `make -j"$(nproc)"` は、package の中でしか並列に動きません。

仮説: C1（C0 に `BR2_PER_PACKAGE_DIRECTORIES=y` を足したもの）は、GitHub の標準 runner で、Buildroot の step の中央値を C0 より 20 % 以上短くする。

候補から外したもの（上限が 20 % に届かない）: QEMU の smoke test の並列化（3 件の合計 46 秒）、開発用イメージの取得（13 秒）、成果物の packaging（64 秒）。

## 条件

| 項目 | C0 | C1 |
|---|---|---|
| base | 同じ `main` の commit | 同じ |
| workflow | `main` の build.yml に、`build-time.log` を集計して `=br-time=` を出す処理と、ccache の場所の判定を足したもの | C0 と同じ |
| defconfig | 変更なし | `BR2_PER_PACKAGE_DIRECTORIES=y` を追加 |
| runner | `main` の build.yml と同じ label | 同じ |
| ccache | workflow の既存の cache（PR ごとの scope）。build の前に `ccache -z` | 同じ |

- 反復: 各条件で、warm-up 1 回と本番 5 回。warm-up は PR で最初の run で、cache の状態がほかの run と違うため集計から外す。
- 順序: C0 と C1 に同時に空の commit を push し、同じ回の run どうしを組にする（時間帯の影響をそろえる）。前の run が終わってから次を push する（PR の concurrency は進行中の run を取り消すため）。

## 測る値

- 主: build job の `=step-time=` のうち `Build image and legal information` の秒数。
- 副: build job 全体の秒数、run ごとの ccache の hit 率（`ccache -z` 後の `=ci-meta=	ccache`）、`=br-time=` の step 別の合計、QEMU の smoke test 3 件の秒数と結果。
- 全 run について、run ID、job ID、commit、結論（success・failure・cancelled）を CSV に残す。

## 採否の基準（結果を見る前に固定）

1. 本番 5 回の主の値の中央値で、C1 が C0 より 20 % 以上短い。
2. C1 の本番 5 回がすべて成功し、build workflow のほかの job と QEMU の smoke test 3 件も成功する。
3. 成果物が変わらない。同じ commit のローカルの build 2 つ（[非 PPD 対照 build](2026-10-21-ci8-ppd-control.md)）で比べ、legal-info の package と version の組が同じで、target の差がすべて説明できる。説明できない差が残る間は採用しない。

失敗した run と取り消された run はログを残し、中央値から外す。外した結果、どちらかの条件で本番が 5 回に満たなければ、その分を追加で走らせる。

## 既知の制約

- 標準 runner の CPU 数はローカル（12）より少ないので、ローカルの 1 回の結果（約 23.5 % 短縮）は CI の結果を予測しない。
- CI の成果物は認証なしでは取得できないため、成果物の比較はローカルの build で行う。

## 結果

全 12 run の build job は成功しました。本番 10 run は C0、C1 とも checks が 10/10 成功しました。C1 の warm-up は `agent-docs` が失敗し、実験文書 2 件の README 一覧への未掲載が理由でした。run ID、build job ID、head SHA、全 checks の結果は [CSV](2026-10-21-ci8-ppd-ci.csv) と [summary marker](2026-10-21-ci8-ppd-ci-markers.txt) に記録しました。

主の値は `Build image and legal information` の秒数です。

| 条件 | warm-up（集計外） | r1 | r2 | r3 | r4 | r5 | 本番中央値 |
|---|---:|---:|---:|---:|---:|---:|---:|
| C0 | 1,024 | 1,240 | 1,245 | 1,083 | 1,218 | 1,201 | 1,218 |
| C1 | 2,922 | 698 | 996 | 832 | 885 | 711 | 832 |

本番の組ごとの短縮率は r1 43.7 %、r2 20.0 %、r3 23.2 %、r4 27.3 %、r5 40.8 % でした。build job 全体（job 開始から最後の step 完了まで）の中央値は C0 が 1,378 秒、C1 が 980 秒でした。

| `=br-time=` の値 | C0 本番中央値 | C1 本番中央値 |
|---|---:|---:|
| wall | 1,126.3 秒 | 744.3 秒 |
| build step 合計 | 667.9 秒 | 747.6 秒 |
| configure 合計 | 254.3 秒 | 438.1 秒 |

step 合計は並列実行された package の所要時間を足すため、wall とは一致しません。ccache の hit 率は本番 run で両条件とも 99.81〜99.89 % でした。cacheable calls は C0 が 22,025 回中 15,917 回、C1 が 21,937 回中 15,914 回でした。C1 warm-up の hit 率は 43.13 % で、PPD による path の変更後に cache が効かなかったため集計から外しました。QEMU smoke test 3 件は全 run 成功し、各 9〜16 秒でした。

## 採否

基準 1 は満たしました。本番 Buildroot step の中央値は C0 の 1,218 秒から C1 の 832 秒となり、短縮率は 31.7 % で、基準の 20 % 以上です。基準 2 も満たしました。本番 10 run は全 checks 10/10 成功し、QEMU smoke test 3 件もすべて成功しました。

基準 3 の legal-info では package と version の組 13 組が一致し、片側だけの組はありませんでした。target の差は module 署名、時刻、build ごとに生成される鍵、埋め込み toolchain path、libv4l の locale と gconv 2 件の RPATH 長で説明できました。一方、`v4l2-compliance` と `v4l2-ctl` の `.rodata` には埋め込み path の長さだけでは説明できない差が残ります。事前登録の「説明できない差が残る間は採用しない」に従い、採否は保留です。不採用とは判断していません。成果物差の記録は[非 PPD 対照 build](2026-10-21-ci8-ppd-control.md)にあります。

## 失敗・逸脱

C1 warm-up では README の実験一覧に文書 2 件がなく、`agent-docs` check が失敗しました。C1 r1 の前に README の一覧だけを修正し、build inputs に影響しない docs-only 変更として記録しました。以後の checks はすべて success でした。run の取り消しや取り直しはありません。

## 未確認の点と次の手

- `-ffile-prefix-map` などで埋め込み path を固定した build を PPD・非 PPD で比較し、module 署名と鍵以外の差を確認します。`BR2_REPRODUCIBLE` がどの差を抑えるかは未確認です。
- v4l-utils を製品に含める必要があるか確認します。
- 標準 runner とローカル（12）の CPU 数の違いを考慮します。
- CI log は GitHub の保持期間後に削除されるため、値を本書の CSV と marker file に保存しました。

## 追記（2026-10-21）

[#30 の path-map 追試](2026-10-21-ci8-ppd-pathmap.md)で、P0 に残った `v4l2-compliance` の 217 B と `v4l2-ctl` の 11,669 B の差を、埋め込まれる host path の長さで説明した。P1 では base と PPD の 6 binary が repeat 間・tree 間で byte-identical になった。これにより、CI #8 の事前登録にある成果物基準 3 を満たした。

この結果は成果物差の説明に関するものであり、PPD の採否は利用者が判断する。採用する場合は `board/cardputerzero/post-build.sh` の seedrng 処理の修正が前提となる。

# QEMU 11.1.2 icount 遅延の bisect による原因コミット特定

- 実施日: 2026-10-31
- 目的: `docs/experiments/2026-10-29-qemu-1112-slowdown.md` で確認した icount 起動の約 8 倍遅延（v11.0.2 → v11.1.2）の原因コミットを特定する
- 結論: 第一 bad コミットは `01b223f895a72106947fae39d39c0cc15d952ba4`（`target/arm: enable WFE sleeping for A-profile`、Alex Bennée、2026-06-24）

## 前提

前回の調査で strace により、遅い側は icount のタイマー deadline ごとに vCPU スレッドとメインループが rendezvous（futex 待ち約 147 万回）する構造を突き止めていた。今回は `git bisect` でどのコミットがその挙動を導入したかを特定した。

## 測定条件（製品に合わせた bisect ハーネス）

| 項目 | 値 |
|---|---|
| machine | `raspi3ap`、`-m 512M` |
| DTB | `output/images/bcm2710-rpi-cm0.dtb`（`/soc/serial@7e201000/bluetooth` を `disabled` に、run-qemu.sh と同じ処理） |
| 起動引数 | `-icount 'shift=0,sleep=off'`、append は sweep と同一（`initcall_debug printk.time=1 msd.sweep=1` 等） |
| パッチ | `docker/qemu-patches/0*.patch` を各コミットに適用（`git apply` 失敗時は `patch --fuzz=3`、それでも不可ならそのパッチのみ省略） |
| 判定 | `MSD/Linux ready` までの実時間が 45 秒以内 = good、超過 = bad。超過時点で即終了 |
| ビルド | debian:trixie-slim、`--target-list=aarch64-softmmu --enable-slirp --enable-fdt=system` 等（msd-dev と同等） |
| イメージ | `output/images/sdcard.img` を 1 GiB に truncate したコピー（旧 QEMU の電源 2 制約対策） |

## ハーネスで踏んだ罠（再現時の注意）

| 現象 | 原因と対策 |
|---|---|
| 全バージョンがゲスト時刻 0.74s で停止 | **カスタムパッチ未適用が原因**。パッチなしの QEMU では `bcm2835_pm_probe` 経由の deferred probe（cam1_regulator の警告トレース）直後に進行しなくなる。4 パッチ適用で解消した |
| 同じく 0.74s 付近で停止 | `bcm2710-rpi-3-b.dtb`（1 GiB 宣言）を `-m 512M` の raspi3ap に与えたため。製品と同じ `bcm2710-rpi-cm0.dtb` に修正 |
| `git bisect run` が同一バイナリを評価し続ける | `git bisect start --no-checkout` で開始すると作業ツリーが動かない。外して解決 |
| bisect がコミット間を移動できない | 前ステップのパッチが作業ツリーに残ると次の checkout が失敗。step スクリプトの開始・終了の両方で `git checkout -- .` する |
| 早すぎるタイムアウトで全件 bad | ready 検出をポーリングし、45 秒のしきい値超過で即打ち切りに変更（bad 側も 1 分以内で判定） |

## 結果

| 判定 | コミット | 実時間（ready まで） |
|---|---|---:|
| good | `v11.0.0`（merge-base）、`c45b02cb24`、`34a7a3eda0`、`6e5f9171c0`、`46d96da130`、`7f2007d192`、`d77a93ca4b`、`272eef0d25`、`6c6e24166f`、`60e7ee5bb7` | いずれも約 15 秒 |
| bad | `3455eac92d`、`079466ae92`、第一 bad `01b223f895` | 48 秒超（打ち切り） |

`git bisect` の最終出力:

```
# first bad commit: [01b223f895a72106947fae39d39c0cc15d952ba4] target/arm: enable WFE sleeping for A-profile
```

直前の good `60e7ee5bb7`（SEV/SEVL for all modes）との境界は明確で、中間コミットでの曖昧な判定はなかった。

## 基準点の実測

| QEMU | パッチ | ready までの実時間 |
|---|---|---:|
| v11.0.2 | あり（0003 のみ fuzz 適用） | 約 15 秒 |
| v11.1.2 | あり | 約 99 秒 |
| v11.1.2 | なし | ready 未到達（0.74s で停滞、上表の罠） |

現行カーネル（PREEMPT_RT・FTRACE off・hardening 採用後）では 11.0.2 → 11.1.2 で約 6.6 倍。前回記録の約 8 倍（旧カーネル構成）と整合する。

## 原因の解釈

`01b223f895` は A-profile で WFE 実行時に vCPU を実際に sleep 状態へ入れ、イベントストリーム用タイマー（`wfxt_timer`）で起床する変更。これにより次の連鎖が起きると考えられる:

1. ゲストのアイドル・排他制御パスで WFE が頻繁に実行される
2. sleep 中 vCPU は `wfxt_timer` の deadline でしか起きない
3. icount ではタイマー deadline のたびに vCPU ↔ メインループの rendezvous が発生
4. rendezvous が futex の wait/wake として実時間を支配（前回測定の約 147 万回）

`git bisect` ログ上、`01b223f895` の直後には `da9b86c35f`（WFET の実装）など関連コミットが続く。v11.1.2 で単純な `git revert` は `target/arm/tcg/translate.c` で後続変更と競合するため、製品側で戻す場合は手動のバックアウトが要る。

## 対処の選択肢（本リポジトリの範囲）

| 案 | 内容 | 評価 |
|---|---|---|
| A. 何もしない | 11.1.2 のまま icount の実時間コストを受け入れる | 現状。起動試験が数分単位で遅い |
| B. sweep/計測を 11.0.2 で実行 | `QEMU_SYSTEM_AARCH64` で別バージョンを指定可能 | 版差の確認用途と両立しない |
| C. `01b223f895` をバックアウトした QEMU | docker/qemu-patches に手動リバートを追加 | icount の速度は戻るが、WFE sleep のアーキテクチャ忠実性を捨てる。後続コミットとの競合解消が必要 |
| D. sleep=off の効果の再確認 | `QEMU_ICOUNT` の組み合わせ | 既に sleep=off で運用中、これ以上の効果なし |

upstream への Issue・PR は方針上実施しない。

## 再現手順

本記録のハーネスは `board/cardputerzero/tools/qemu-bisect/`（`run-bisect.sh`・`step.sh`）として製品条件で再現可能に整備した。次の実行で本調査と同じ bisect が走る:

```sh
board/cardputerzero/tools/qemu-bisect/run-bisect.sh v11.1.2 v11.0.2
```

要点は上記「測定条件」と「罠」の表の通りで、パッチ適用（fuzz 含む）と ready 検出・しきい値判定を step.sh が担う。

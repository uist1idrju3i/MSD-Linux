## 目的・基準・回数

LCDと内部keyboardの準備が失敗したまま、S02の/data処理へ進まないことを確認します。
実行前の判定条件は、hostで正常・欠損・期限・module順序を確認し、
QEMUではA/Bとも終了0・4 markerの順序・/data・readyを要求するものです。
例外を無効にした負対照では、failedとboot blockedを要求し、/dataとreadyは拒否します。
softwareの制御確認であり、性能の結論・中央値は出しません。
先行03は各1回、最終04のA/Bは初回失敗・単独再試行各1回、不在例外とmodule期限の対照は各1回です。

## 手順と対照

[fixture生成器](../../board/cardputerzero/tools/bench/early-io-fixture.py)で再packし、
[設計のコマンド](../design/early-io.md#再現手順)で`test-boot.sh`と`test-ab.sh`を実行します。
今回の03・04・期限対照は、02で構築したBusyBoxを`--busybox output-early-io-02/busybox/busybox`で再利用しました。
01・02の経緯は下記に残します。新規directoryを指定すれば、BusyBoxの再構築から再現できます。

負対照はAの環境に`QEMU_EXTRA_APPEND=msd.early_io=required QEMU_BOOT_TIMEOUT=45`を加えたものです。
launcherのqemu modeと重複し、hardware-absent例外を拒否します。
45秒はhost試験器の監視期限であり、helperの20秒期限とは別です。
host側の偽sysfs試験では1秒のmodule期限と、bind・DRM・fb・backlight・input・keymap・symlinkの不備を確認しました。

QEMUのmodule期限対照は、生成器の`--module-timeout`で別fixtureを作り、Aの試験器を45秒監視で実行したものです。
RAM上の偽DT・firmware/keymapを使い、最初のmodprobeを30秒sleepへ差し替えます。
製品helperとBusyBox timeoutは最終04と同じで、期限だけ3秒です。実driverはloadしません。

A/Bとも次の順序です。skippedは実hardwareのbind・入力の成功を意味しません。

```text

```

両slotでQMP quit・returncode 0・reaped true・fallback空を確認しました。
これは最終04の単独再試行の結果です。不在例外の対照はfailed・boot blockedで止まり、/data markerとreadyはありません。
module期限の対照は次のとおりです。いずれも試験器は期待どおり124で終了しました。

```text
[    9.682962] msd-early-io: early-io begin; safe to power off
[   10.444400] early-io-fixture: sleeping modprobe gpio-forwarder
[   11.441085] msd-early-io: waiting elapsed=2 limit=3; safe to power off
[   12.483914] msd-early-io: early-io end failed
Early I/O failed; boot blocked.
```

beginからfailedまで2.800952秒で、/dataとreadyはありません。整数秒の丸めを含む3秒設定の制御確認であり、
既定20秒・実driverの停止時間や、割込み不能なkernel処理の保証には転用しません。
通常logには既存のpartition再読込みのbusy、QEMUのmmc1 timeoutとLEDのdeferred probeがあります。
これらを新しいLCD・keyboardの実probeの証拠とは扱いません。

## 失敗した構築と未確認

最初の`output-early-io`はunsquashfsの所有者変更が権限不足で終了2でした。
fakerootを使う修正後、別の`output-early-io-02`で構築成功しました。02はbootしていません。
helperの進捗表示を直した版を03へ再packし、先行の3 bootを行いました。
03の3 bootは成功した後、電源を切れる旨を英日でそろえた最終版を04へ入れました。
04のA/B・不在対照・期限対照を4並行で実行したところ、A/Bはready後のQMP処理で失敗しました。

```text
"qmp_quit": false, "returncode": 0, "reaped": true, "fallback": ["SIGTERM"], "error": "timed out"
```

`boot-test.py`はready後に5秒のgraceでQMPを呼び、socketのtimeoutを同じerror欄へ記録します。
既定のboot監視期限300秒を使い、hostに`QEMU_BOOT_TIMEOUT`指定はありませんでした。
単独の再試行は監視期限120秒に明示変更し、A/BともQMPを含めて成功しました。
並行負荷との関係は推測で、timeoutしたQMP応答の種類と遅延の直接原因は未確認です。
この失敗を成功へ書き換えず、元の構築出力・失敗logは削除していません。

製品full build、実機のLCD表示・backlight・keyboard・firmwareの実probe、I2C/SPI、
SD write・FTL、電断、実機watchdogは未確認です。今回の速度・容量の改善は主張しません。
hostの期限試験はhostのtimeout、QEMUのmodule期限対照はguestのBusyBox timeoutを使います。
実deviceを待つ既定20秒経路と、実機の停止時間の確認は残件です。

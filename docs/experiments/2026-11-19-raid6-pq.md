# RAID6 PQ起動benchmarkの省略

## 目的と事前の基準

Linux 6.18.59の`CONFIG_RAID6_PQ_BENCHMARK`だけを無効にし、PQ libraryとBtrfsを残す。基準は`8eab8b6`、Buildrootは`75f325ad84251ee9d903467f84d3683e3bcf3fd5`。別worktreeと専用の`O=output-raid6-pq`を使い、実行中の851-probe smokeのsource・出力・processへ変更を加えない。

採用の条件は、生成済みconfigの`RAID6_PQ=y`とbenchmark無効、benchmarkのthroughput行消失とskip行出現、Btrfs single/DUPのmount・書込み・読戻し・scrub成功である。起動時間は記述統計とし、host負荷が共存するQEMUだけで実機の高速化を認定しない。

正式測定はA=benchmark有効、B=無効をABAB順で各5回。別にA/Aを2回行う。各回でhost loadを採り、kernelの時刻付きboot完了marker、PQ選択algorithm、raid6全行を保存する。rootfs、DTB、QEMU binary・machine・CPU・memoryと起動方法を固定する。初期化した同一imageの写しを毎回使う。Btrfs probeはboot完了markerの後にRAM上の使い捨てimageで実行する。

## 未確認

実機時間、実機で選ばれるalgorithm、実SDの物理write、RAID5/6 profileの機能・性能は未確認。`crypto/xor.c`の別の較正は変更対象外である。

### 時間と負荷

`RAID6_BOOT_COMPLETE uptime=`は、BusyBox initが通常の`/etc/init.d/rcS`を走らせ、最後の測定hookへ入った時点の`/proc/uptime`である。その後にRAM内のBtrfs probeを実行する。独自hookを含むQEMU上の完了点であり、実機の画面表示時刻ではない。

CSVの`boot_seconds`はこのguest時刻。`wall_marker_seconds`はwrapper起動からmarker受信までで、imageのcopy・hashなども含む。`host_load_*`はhost全体の1分load averageの開始・終了・最小・最大。各回の`load.json`には経過時間と1/5/15分のload averageを残す。benchmark単体のCPU使用率とは扱わない。`initcall_debug`は渡したがDEBUG行はconsoleに出なかったため、initcall個別の時間はCSVでは空欄であり、0秒ではない。

851-probe smokeは開始時にPID `1145717`の生存を確認したが、RAID6測定前に21件目の`E2/T1-negative-final`で停止していた。20件成功後、logに`error=t1_negative_final_checker_validation_failed`、coverageに`ok=false`、stage4に`smoke failed: E2/T1-negative-final`が残った。所要356.997秒で、記録された直接の停止理由はguestの負対照検査の失敗である。flagを追加する前の出来事で、元worktreeのsourceやprocessへ変更・signal送信・再起動はしていない。構築時のhost負荷との関係は未切分けである。測定時に851 smokeが負荷を掛け続けていたとは扱わず、追加の人工負荷も与えていない。ABAB順と各回の負荷記録はそのまま維持した。

## 構築と測定の手順

測定器は[run.py](../../board/cardputerzero/tools/bench/raid6-pq/run.py)、guest hookは[guest.sh](../../board/cardputerzero/tools/bench/raid6-pq/guest.sh)。`prepare`は既存出力を上書きせず、`measure`は既存CSVを上書きしない。失敗した回もCSV・result・serialへ保存して止まる。guestが終わった後にQMPでquitし、QEMUの終了状態と残りのserialを確認する。

worktreeをcontainerの`/work`へmountするほか、submoduleの相対Git参照用aliasを用意した。以下の`dev`は実行したmountの構成を変数で表したもの。元worktreeのsourceはmountしない。共通Git metadataは読取り専用とし、この別worktree自身のmetadataだけを書込み可能にする。

```sh
common=$(realpath "$(git rev-parse --git-common-dir)")
own_git=$(realpath "$(git rev-parse --git-dir)")
primary=$(basename "$(dirname "$common")")
worktree=$(basename "$PWD")
dev() {
  docker run --rm --user 0:0 \
    -e GIT_CONFIG_COUNT=1 -e GIT_CONFIG_KEY_0=safe.directory \
    -e GIT_CONFIG_VALUE_0=/work \
    -v "$PWD:/work" -v "$PWD:/$worktree:ro" \
    -v "$common:/$primary/.git:ro" -v "$common:$common:ro" \
    -v "$own_git:/$primary/.git/worktrees/$(basename "$own_git")" \
    -v "$own_git:$own_git" -w /work msd-dev:local "$@"
}
dev make -C vendor/buildroot BR2_EXTERNAL=/work \
  O=/work/output-raid6-pq msd_cardputerzero_defconfig
dev make -C output-raid6-pq BR2_JLEVEL=16
dev make -C output-raid6-pq BR2_JLEVEL=16 linux-reconfigure
dev python3 board/cardputerzero/tools/bench/raid6-pq/run.py prepare \
  --output output-raid6-pq --runs raid6-runs
```

Aはflag追加前の基準fragmentで構築した。Aの`images/Image`と`build/linux-custom/.config`を`raid6-runs/A/{Image,config}`へ保存した後、fragmentへ`# CONFIG_RAID6_PQ_BENCHMARK is not set`を追加し、次を実行した。Bも同じように`raid6-runs/B/`へ保存し、config差分とimageの読戻しhashを確認してから起動した。

```sh
dev make -C output-raid6-pq BR2_JLEVEL=16 linux-reconfigure
dev make -C output-raid6-pq BR2_JLEVEL=16
dev python3 board/cardputerzero/tools/bench/raid6-pq/run.py measure \
  --output output-raid6-pq --runs raid6-runs
```

probeは256 MiBのRAM上のimageへ`mkfs.btrfs -d single -m dup`し、mount、256 KiB書込み、sync、unmount、remount、SHA-256読戻し検査、`scrub start -B -R`、unmountの順に行う。元のSD imageのfilesystemをprobe用に再formatしない。kernelのpanic/Oops/BUG、guest失敗、profile欠落、scrub counter欠落・重複・非0、QEMU異常終了は成功にしない。

## 構築の失敗

最初のcontainerは、worktreeのsubmodule `.git`にある相対参照を解決できず、`M5STACK_CARDPUTERZERO_VERSION is empty`で構築前に停止した。独立worktreeのsourceと共通Git metadataの読取り専用aliasをcontainerへ渡し、`git -C vendor/buildroot rev-parse HEAD`で参照を確認してから、別logで再実行した。元worktreeのsourceはmountせず、Gitの永続設定も変更していない。

続く構築はexit 0だったが、Gitのindex refreshが読取り専用metadataで失敗した。共通metadata全体を読取り専用にしたまま、別worktree自身のmetadataだけを書込み可能にして解消した。最終A/Bの構築logにこのfatalはない。

`linux-rebuild`では`comm: ... .files-list.before: No such file or directory`が出た。Buildrootの`pkg_size_before`はconfigure段階で作成し、install後の`pkg_size_after`が消すため、configureを飛ばすrebuildでは不足する。A/Bとも`linux-reconfigure`へそろえて解消した。警告のあった回のpackage容量統計は使わず、logは保存した。

module全1038件の完全一致を仮定した確認も一度失敗した。差は埋込みconfigを持つ`configs.ko.xz`の1件だけだった。生成configの1行差と同じ署名証明書を確認し、共通rootfsによる比較条件とconfig確認方法を上記のとおり明記した。ここまでにQEMUの失敗試行はない。

## 結果

提出用CSVは改行だけをLFにそろえた。archive内の元CSVは変更していない。

[生のCSV](2026-11-19-raid6-pq.csv)は実行順の12行。A/Aの2回に続き、ABABを5組、直列に実行して全回成功した。失敗bootは0件。A/Aの完了時刻は29.32秒と30.13秒、algorithmはそれぞれ`neonx4`と`neonx8`で、同じAでも計測値と選択が揺れた。

| 正式測定 | 回数 | 起動完了中央値、秒 | 最小〜最大、秒 | 選択algorithm |
|---|---:|---:|---|---|
| A、benchmark有効 | 5 | 29.73 | 29.30〜30.03 | neonx2が2回、neonx4が2回、neonx8が1回 |
| B、benchmark無効 | 5 | 28.57 | 28.23〜31.44 | neonx8が5回 |

中央値の差は1.16秒だが、2組目と5組目ではBの方が遅い。A/Aの差は0.81秒であり、host負荷やQEMUの揺れを含む小標本から起動時間の一定量の改善を保証しない。正式測定のhost loadの開始・終了値は1.45〜2.35の範囲で、各回の最小・最大と全sampleはCSVとarchiveに残した。

Aでは各回10行のgen/xor throughputが出た。Bでは全回0行となり、代わりに次のskip行が出た。recovery選択は残り、別のXOR較正の開始・選択logも全12回に残った。

```text
raid6: skipped pq benchmark and selected neonx8
raid6: using neon recovery algorithm
xor: measuring software checksum speed
xor: using function: 8regs (...)
```

最後の行の速度値は回ごとに異なるため省略表記とした。QEMU上のMB/sを実機の演算性能とは扱わない。`crypto/xor.c`の較正を止めたという結果でもない。

全12回でBtrfsの`Data, single`と`Metadata, DUP`を確認し、mount・書込み・remount後のSHA-256読戻し・scrubが成功した。`read_errors`、`csum_errors`、`verify_errors`、`uncorrectable_errors`は全回0。`RAID6_BTRFS_OK`、guest exit 0、QEMU exit 0も全回そろった。single/DUPではRAID5/6 parity recoveryを実行していないため、その機能・性能の確認には広げない。

事前の機能条件を満たしたので、製品fragmentにはbenchmark無効を採用する。RAID6 PQ library、Btrfs、独立したXOR較正は残す。実機時間・実機での最適algorithm・物理SD write・RAID5/6 profileは未確認である。

## 証拠とhost検査

[証拠archive](2026-11-19-raid6-pq-evidence.tar.gz)は57 file、1,038,430 byte。SHA-256は`3e05b4524e48b32fd5bdf626b548d2abdbe053321895e46dfde31995be6253bc`。`manifest.json`で全memberのsizeとhashを読戻し照合した。12回のserial・負荷sample・result、A/B生成configとmodule hash、入力hash、環境情報を保存した。大きなimageと秘密の署名鍵は含めない。imageのhashは上表と各serialにもある。

review前のarchiveには7,322,860 byteの`build-A-02.log`など、完全な構築logを含めていた。大きなlogをcommitしない規則に合わせ、構築log全8件を別に保全・照合し、archiveから外した。代わりに`build-log-index.json`へ各logのsizeとSHA-256、`build-log-excerpts.txt`へ失敗行と先頭・末尾の抜粋を保存した。最大logのSHA-256は`c841332b196232e38460dfebb441d1b39ce4beca598383c00580ddddd64b32a1`。再生成する場合は上記の構築手順でstdout/stderrを保存する。初期のGit mount不足などを再現しなければ、当時の失敗logとbyte単位で一致するとは限らない。

parserは正常2例、空・失敗・近似例14例で検査した。実際の12 logも再解析し、AをB、BをAと誤指定した場合は拒否することを確認した。host aggregateは11 suiteが成功し、追跡対象のShellCheckも成功した。日本語・リンク・文書サイズ・実験索引の検査は提出前に実行する。

### review後の測定器修正

測定時のsourceは`0fdda0b`。その後、継承した`QEMU_DRIVE_FILE`を除去し、wrapperが測定用copyを使うよう修正した。当初のDocker起動commandはこの環境変数を渡しておらず、使用imageにも同名のENVやentrypointがないことを確認した。既存12回の測定結果は変更せず、起動の再測定もしていない。

`prepare`は未作成の親directoryを作り、repo外の`--runs`では絶対pathを記録する。repo内では従来どおり相対pathを使う。path表記はimageを生成する前に検証し、既存の`prepared`を上書きしない。回帰検査は`python3 board/cardputerzero/tools/bench/raid6-pq/test_run.py`で実行する。

# S16: `/etc`・`/data` の通常 read-only 化の QEMU 検証

[読み取り専用領域と FS 比較](../research/readonly-data-and-fs.md) の「提案する read-only policy」に対し、QEMU で writer の失敗様式・maintenance window の基本動作・電源断後の fsck 差を確かめた。製品の mount 設定は変更していない。

## 条件

- 基準: `origin/main`（このブランチの起点）で構築した `output/images/sdcard.img` を `output/s16-test.img` に複製し、1 GiB に padding したもの（QEMU の SD モデルは 2 の冪のサイズのみ受け付ける）。
- QEMU: msd-dev イメージ内の QEMU 11.1.2、`raspi3ap`、512 MiB、icount なし。`run-qemu.sh` に `QEMU_COPY_IMAGE=0` を渡して書き込みを同じ image に残した。
- 各 run はシリアルにコマンドを注入し、終了は `timeout` による強制終了（電源断相当）。

## 手順と生の値

### Run A: remount 後の writer の失敗様式

起動直後 `/data` は rw（`rw,nosuid,nodev,noatime,errors=remount-ro,data=ordered`）。`/etc` は overlay（`lowerdir=/data/etc:/etc`、`upperdir=/run/etc-overlay/upper`=tmpfs）で、`/etc` への書き込みは tmpfs upper にだけ入ることを `touch /etc/zzz-volatile` で確認（`/run/etc-overlay/upper/zzz-volatile` が生成、`/data/etc` は無変化）。

`mount -o remount,ro /data` 後の各 writer:

| writer | 結果 |
|---|---|
| `touch /data/zzz` | `touch: /data/zzz: Read-only file system` |
| `seedrng --seed-dir=/data/seedrng` | `seedrng: can't remove file 'seed.credit': Read-only file system` |
| `mkdir -p /data/zzz-mkdir` | `mkdir: can't create directory ...: Read-only file system` |
| `msd-data-grow` | resize2fs が `The filesystem is already 90112 (4k) blocks long. Nothing to do!` で終了（成長済みのため書き込み不要の経路のみ確認） |

maintenance window の基本形 `remount,rw` → 書き込み → `sync` → `remount,ro` は動作し、`persist-A` を書いたファイルがこの run 内で読めた。

### Run B: ro マウント中の強制終了 → 再起動

`fsck.ext4 -p` は `data: clean, 17/49152 files, 4163/90112 blocks` で、journal recovery なし。dmesg にも recovery 行なし。`persist-A` は残っていた。2 回目の起動で `msd-data-grow` のパーティション拡張は再実行されず、resize2fs は `Nothing to do`。その後 `remount,rw` で未 sync の `dd` 2 ファイル（各 262,144 B）を残したまま強制終了。

### Run C: rw マウント中の強制終了 → 再起動

`fsck.ext4 -p` が `data: recovering journal` → `data: clean, 19/49152 files` と journal replay を自動実行し、起動は問題なく続行した。強制終了前に書いた 2 ファイルは残っていた。

## 結論

- `/etc` は現行構成の時点で事実上「通常 RO」相当である: 書き込みは tmpfs upper にのみ入り、`/data/etc`（lower）への書き込み経路は稼働中に存在しない。S16 の `/etc` 項目は「永続設定の保存経路を新設するか」の設計問題に絞れる。
- `/data` を通常 ro にする場合、writer は全て EROFS で失敗する。seedrng は失敗しても起動は続く（S05 が `|| true`）が、次回起動用の seed 保存は止まるため、ro 既定化には maintenance window か停止時の書き込み手順が必要。
- maintenance window の primitive（ro→rw→書き込み→sync→ro）は現行スクリプト無改造で動作する。
- ro マウント中の電源断は次回起動で journal recovery すら発生しなかった。rw 中の電源断は `fsck.ext4 -p` の自動 journal replay で透過的に回復した。いずれも起動を阻害しない。

## 失敗した試行

- `QEMU_IMAGE=<path>` を環境変数で渡しても `run-qemu.sh` が内部で同じ変数名を使うため無視される。image は位置引数で渡す（本記録は引数で実行）。
- `QEMU_COPY_IMAGE` を付け忘れた run では、書き込みが一時コピーに入り再起動で失われた（`zzz-persist` 消失で判明）。
- `QEMU_COPY_IMAGE=0` では padding なしの 736 MiB image を QEMU が `Invalid SD card size` で拒否した。1 GiB に `truncate` で padding して解決。
- 引数なしの `seedrng` は `/var/lib/seedrng`（squashfs 上）を使うため、`/data` の writer としての試験にならなかった。

## 未検証

- resize が本当に必要な状態で ro マウントされた `/data` への `resize2fs`（オンライン resize の失敗様式）。
- `fsck.ext4 -p` が `-p` で直せない損傷（要 `-y` / 手動）になった場合の起動継続性。
- maintenance window を組み込んだ init 設計（排他、失敗時の ro 復帰、seedrng の停止時実行）の実装と検証。
- 実機 SD カードでの再現。QEMU の SD モデルの電断模擬はホスト強制終了であり、実カードの FTL の振る舞いは含まない。

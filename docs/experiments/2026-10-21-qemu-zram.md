# zram swap の QEMU 試験

- 状態: 完了（QEMU のみ。実機と製品への組み込みは未確認）
- 日付: 2026-10-21
- 担当: Devin
- 関連: docs/research/simulation-plan.md の小項目「zram」、docs/research/cpu-irq-and-sysctl.md、docs/research/power-and-updates.md の 6.6

## 目的と仮説

いまのカーネル（`CONFIG_ZRAM=m`）で zram を swap として使えるか、そのとき zswap が無効のままかを確かめます。あわせて、zstd と lz4 の圧縮率と、設定にかかる時間を記録します。

仮説: 追加のパッケージなしで、`modprobe zram` から `swapon` まで動きます。rootfs の `/sbin/swapon` は util-linux の版で、`-p` で優先度を指定できます（BusyBox の `FEATURE_SWAPON_PRI` は無効ですが、使いません）。

## 採否の基準（結果を見る前に書く）

各 algorithm（zstd、lz4）を 5 回、icount（`QEMU_ICOUNT=shift=0`）で起動します。

- Z1: `modprobe zram` と `swapon -p 100 /dev/zram0` が成功し、`/proc/swaps` に priority 100 で載る。
- Z2: `/sys/module/zswap/parameters/enabled` が `N` のまま。
- Z3: 450 MiB の tmpfs に `/dev/zero` 由来の 400 MiB（4 MiB を 100 回連結）を書いても OOM が起きず、`mm_stat` の orig_data_size が 0 より大きい。

5 回とも Z1〜Z3 を満たせば、その algorithm は QEMU で「使える」とします。`/dev/urandom` 由来の 400 MiB も続けて書きますが、圧縮が効かないので OOM を含めて記録だけにします（合否に使いません）。

最初の計画には「`MSD/Linux ready` の icount 中央値が基準より遅くならない（Z4）」がありました。試験用 hook は `S99zz` で `S98msd-ready` より後に動くので、ready の時刻は hook の影響を受けません。そのため、どの試行も始める前に Z4 と基準 5 回を取り消し、hook の設定にかかる時間（`modprobe` から `swapon` まで）の記録に替えました。

## 手順

```sh
docker/msd-dev board/cardputerzero/tools/bench/data-noexec/make-variant.sh zram output/s27/zram \
    board/cardputerzero/tools/bench/zram/S99zz-zram-probe
docker/msd-dev env QEMU_ICOUNT=shift=0 board/cardputerzero/tools/bench/zram/run-zram.sh \
    output/s27/zram /work/output/s27/zram-logs/zstd-icount-r1.log zstd
# 追加の試行（圧縮できる非 zero のデータ）
docker/msd-dev env QEMU_ICOUNT=shift=0 ZRAM_EXTRA_APPEND=msd.zram_loads=text \
    board/cardputerzero/tools/bench/zram/run-zram.sh output/s27/zram-text \
    /work/output/s27/zram-text-logs/zstd-text-r1.log zstd
python3 board/cardputerzero/tools/bench/zram/summarize-zram.py <serial.log...> > docs/experiments/2026-10-21-qemu-zram.csv
```

3 本ずつ並列に実行しました。serial のログは各 30 KiB 前後で、コミットしていません。CSV の `log_sha256` に各ログの SHA-256 を残し、上の手順で作り直せるようにしています。

## 結果

生の値は [2026-10-21-qemu-zram.csv](2026-10-21-qemu-zram.csv) です（`mm_stat` の 9 列、swap の使用量、MemAvailable、OOM の回数を含みます）。

| 項目 | zstd（5 回） | lz4（5 回） |
|---|---|---|
| Z1: `swapon` の終了値、priority | 0、100（5/5） | 0、100（5/5） |
| Z2: zswap | `N`（5/5） | `N`（5/5） |
| Z3: zero 400 MiB | 100 個すべて書けた、OOM 0（5/5） | 同じ（5/5） |
| zero のときの orig_data_size | 24,576〜167,936 B | 36,864〜282,624 B |
| zero のときの swap 使用量 | 36,560〜43,252 KiB | 34,224〜46,972 KiB |
| 設定の時間（icount） | 0.040〜0.050 秒、中央値 0.04 秒 | 0.040〜0.050 秒、中央値 0.04 秒 |
| 設定の時間（TCG、1 回） | 1.02 秒 | 0.68 秒 |
| urandom 400 MiB（記録のみ） | 92〜93 個目で `dd` が OOM で止まる。圧縮率 1.00〜1.01、huge_pages 32,505〜32,640 | 91〜93 個目で同じ。圧縮率 1.00〜1.01、huge_pages 32,542〜32,647 |

lz4 と zstd の両方で、5 回とも Z1〜Z3 を満たしました。QEMU では、どちらの algorithm でも zram を swap として使えます。

### zero ページは zram に届いていない

zero の負荷では swap を 34〜47 MiB 使っているのに、zram の orig_data_size は最大 276 KiB でした。Linux 6.18.57 の `mm/page_io.c` は、全体が 0 のページを swap の zeromap に記録するだけで、I/O をしません（`is_folio_zero_filled()` と、「Use a bitmap (zeromap) to avoid doing IO for zero-filled pages.」のコメント）。swap の使用量と orig_data_size の差は、この処理で説明できます（推測。この処理が動いたことを直接は観測していません）。このため、Z3 の zero の負荷は「OOM にならない」ことの確認にはなりますが、zram の圧縮の確認にはなっていません。

### 追加の試行: 圧縮できる非 zero のデータ（本試行の結果を見たあとに決めた。合否に使わない）

`yes 'MSD/Linux zram probe 0123456789 abcdefghijklmnopqrstuvwxyz' | head -c 4194304` を 100 回連結して書きました（icount、各 3 回）。

| algorithm | zram に入った量（orig_data_size） | 圧縮率（orig/compr） | OOM |
|---|---|---|---|
| zstd | 39,813,120〜43,319,296 B | 51.52、52.09、52.41 | 0（3/3） |
| lz4 | 41,037,824〜43,638,784 B | 47.27、47.70、47.83 | 0（3/3） |

同じ文を繰り返したデータなので、圧縮率は実際のアプリのメモリーより大きく出ます。上限の目安として扱います。

## 結論

- QEMU では、いまのカーネルと rootfs のまま（追加のパッケージなし）、zstd と lz4 のどちらでも zram swap を使えました。zswap は無効のままでした。
- 設定にかかる時間は icount で 0.04〜0.05 秒です。起動時に入れても、起動時間への影響は小さいと見込みます（実機では未確認）。
- 圧縮できないデータでは zram も RAM を使うので、OOM は防げません。zero のページは zram を通らずに処理されます。
- 製品に入れるかどうか（init script、`disksize`、algorithm、`swappiness`）は、使うアプリのメモリーの量と、実機での CPU の負荷を見てから決めます。この PR では製品の設定を変えていません。

## 確認できていないこと

- 実機での圧縮と展開の CPU 時間、温度、電力。QEMU の秒数は比較の目安です。
- 実際のアプリのメモリーでの圧縮率。
- zram を `/run` や overlay の upper（tmpfs の代わり）に使う案。

## 失敗した試行と計画の変更

- lz4 の本試行の 5 回目（`lz4-icount-r5`）: 試行中に私が `run-zram.sh` を編集した（追加の試行のための `ZRAM_EXTRA_APPEND`）ため、実行中の bash がスクリプトを読み違え、25 行目で構文エラーになりました。ゲストの結果は出ていません。CSV には `valid=0` で残し、編集後の `run-zram.sh`（`ZRAM_EXTRA_APPEND` が空なら、ゲストに渡す cmdline は前と同じ）で `lz4-icount-r5b` として測り直しました。集計には r5b を使っています。
- 予備試行 2 回（`pilot-zstd`、`pilot-none`）: hook と runner の動作確認です。`pilot-none` は algorithm を指定しない起動で、hook が `skipped` を出すことを確かめました。集計に入れていません。
- 計画の変更: 上に書いた Z4 の取り消しと、zero ページについての追加の試行です。

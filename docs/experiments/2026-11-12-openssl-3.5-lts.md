# OpenSSL 3.5.9 LTSへの外部override

## 目的・条件・採否基準

2026-11-12の利用者決定に従い、Buildroot 2026.08.xを維持してOpenSSLだけを3.6.5から3.5.9へ替える。11月10日のadvisory修正はbackportしない。3.5.10と2026.11.x→2027.02 LTSへの基盤更新は別作業とする。

依頼時の採否基準は、host/targetとも3.5.9であること、通常build・A/BのQEMU起動・署名の正常/拒否試験が成功すること、版・hash・legal-infoの整合、画像とfile一覧の差を説明できること。以下はbuild開始後、結果が出る前に文書へ転記した基準である。1回ずつの構築・機能確認とし、性能差や統計的同等性は判定しない。

基準commitはfresh origin/mainの`8a4f3cb37bf97db86b9e8c65ed5a60da64de6b8c`。変更側もこのcommit上の未commitの外部overrideを入力とした。Buildroot gitlinkは両側とも`8b238854d909c9cce32ef9671d968b03e323b55d`。比較する入力はmainの正規化defconfigと、`BR2_PACKAGE_OVERRIDE_FILE`を追加した変更側である。実験script・kernel fragment・製品の署名鍵設定は変えない。先行調査の基準`8173185`とbuildの基準を混同しない。

| 条件 | 基準 | 変更側 |
|---|---|---|
| O= | `/work/output-openssl-main` | `/work/output-openssl-lts` |
| target/host OpenSSL | 3.6.5 | 3.5.9 |
| recipe / patch | 固定Buildrootのもの | 同じ。追加tarball/license hashのみ外部tree |
| output tree | 新規 | 新規 |
| cache | 既存download cache、共通`.ccache`を再利用 | 同じ。実行順でwarm状態が変わるためbuild時間は比較しない |
| Docker | `docker/msd-dev`、QEMU 11.1.2、host GCC Debian 14.2.0-19 | 同じ |
| host kernel | Linux 7.0.0-43-generic x86_64 | 同じ |

build timestamp・出力path・生成鍵などの非決定要因は揃えていない。Imageのhashや圧縮rootfsの差をすべてOpenSSLの差とは帰属しない。kernelの正規化設定とOpenSSL file一覧を別に比較する。

## 手順

mainのdefconfigから基準のO=を先に作成し、変更後のdefconfigから別のO=を作成した。再現時は基準commitの清潔なcheckoutを使い、次の出力先だけを変える。

```sh
docker/msd-dev make -C vendor/buildroot BR2_EXTERNAL=/work O=/work/output-openssl-main msd_cardputerzero_defconfig
docker/msd-dev make -C output-openssl-main -j8
# 外部overrideを含む変更側のcheckoutで実行
docker/msd-dev make -C vendor/buildroot BR2_EXTERNAL=/work O=/work/output-openssl-lts msd_cardputerzero_defconfig
docker/msd-dev make -C output-openssl-lts -j8
```

採否にはmake変数だけでなく、hostのCLI実行、targetのQEMU内CLI実行、binaryの版情報を使う。`libssl.so.3`は両版とも完全なpatch版文字列を持たないため、SONAME、依存先`libcrypto.so.3`、生成sourceの版とfile hashで対応付ける。CLIとlibcryptoの版文字列は3.5.9を確認する。QEMUは元imageを変更しない既定のcopy方式を使う。`OUTPUT_DIR`と`QEMU_LOG_DIR`を各runへ指定し、`test-boot.sh`と`test-ab.sh`を各1回実行する。署名回帰は変更側のhost OpenSSLをPATHの先頭にして`tests/msd-update/run.sh`を実行する。

## 結果

両方の通常full buildとlegal-infoは終了値0。QEMUのA/B起動は両方とも成功した。基準はAが26秒、Bが24秒、変更側はAが25秒、Bが24秒でready/loginへ到達した。各1回の機能確認であり、起動時間の優劣は判定しない。

```text
OpenSSL 3.5.9 29 Sep 2026 (Library: OpenSSL 3.5.9 29 Sep 2026)
All msd-update host tests passed.
ok - QEMU target OpenSSL CLI/library 3.5.9, Ed25519 verify and tamper rejection
```

版表示の1行目はhostとQEMU内targetの両方で得た。targetの動的loaderは`libssl.so.3`と`libcrypto.so.3`をrootfsの`/usr/lib64/`から解決し、default providerも3.5.9と表示した。追加のtarget試験では、RAMの`/tmp`で試験用Ed25519鍵と署名を作り、`pkeyutl -verify -rawin`で正常なpayloadを受理し、変更したpayloadを拒否した。再現時は`run-qemu.sh`でrootへloginし、`openssl version -a`、`LD_TRACE_LOADED_OBJECTS=1 /usr/bin/openssl`、`openssl list -providers`を実行する。試験鍵は製品の署名鍵ではない。

### サイズとfile一覧

生の値・image/config/logのSHA-256は[測定CSV](2026-11-12-openssl-3.5-lts.csv)、最終target全体とhost OpenSSLの各fileは[file一覧CSV](2026-11-12-openssl-3.5-lts-files.csv)に記録した。sizeは通常fileの論理byte数で、symlinkは合算しない。

| 対象 | main 3.6.5 (byte) | 3.5.9 (byte) | 差 |
|---|---:|---:|---:|
| Image | 18,016,768 | 18,016,768 | 0 |
| rootfs.squashfs | 20,729,856 | 20,680,704 | -49,152 |
| sdcard.img | 771,751,936 | 771,751,936 | 0 |
| target全通常file | 37,265,280 | 37,099,270 | -166,010 |
| target OpenSSL通常file | 7,413,380 | 7,246,628 | -166,752 |
| host OpenSSL通常file | 25,650,008 | 25,281,246 | -368,762 |

target全体は各1,700 file/symlink、うちOpenSSLは各11、host OpenSSLは各167で、全体・OpenSSLともpathの追加・削除は0。packageの`.files-list*.txt`を所有元として、build終了後に残る通常file/symlinkと照合した。CSVは両側計3,734行。symlinkはリンク先、通常fileはsize/hashを記録した。

Buildroot設定の差はoverride指定と`BR2_EXTERNAL_MSD_VERSION`のdirty表示だけ。kernel設定はcommentの説明文と順序を除いて照合し、同一だった。`BR2_REPRODUCIBLE`は未設定で、Imageのhashは異なる。OpenSSL以外では503個の`.ko.xz`に正味+744 byte、`libstdc++.so.6.0.33-gdb.py`に-2 byteのsize差がある。後者の出力先path差を含め、OpenSSLだけの効果と全体のsize差を混同しない。module差の原因の内訳は分離していない。

### legal-infoと監査

変更側のtarget/host両manifestは`libopenssl,3.5.9,Apache-2.0,LICENSE.txt,openssl-3.5.9.tar.gz`を示した。両方の保存licenseのSHA-256は外部`.hash`と同じ`7d5450cb2d142651b8afa315b5f238efc805dad827d91ba367d8516bc9d49e7a`。全体のlegal-infoには両側共通でBuildroot source未保存、外部toolchainのlicense未定義、M5 local sourceのhash未定義の警告が残る。firmwareのlicense不明も残る。配布上のlegal-infoがすべて完結したとはしない。

SBOMは`show-info`から生成し、`set-kernel-version.py`でLinuxを6.18.59へ補正した。同一NVD feed `8a4923e39b78c11670a9a74ba88071d0093ce502`（2026-11-03のfeed commit）を更新せず比較した。両側とも67 componentで、CPE照合の`exploitable`状態はtarget 142件・host 7件のaffected-ref。OpenSSLの該当CVEは両側とも0だった。これは11月10日のadvisoryを網羅する最新検査ではなく、CPE照合は実際の到達性を証明しない。

### 失敗した試行

- 最初のserial追加probeは、非TTY時の`docker/msd-dev`がstdinを渡さないためloginで停止した。`docker run -i`で同じimage/kernel/DTBを使ったprobeは成功した。通常のA/B試験は初回で成功した。
- libsslに完全な版文字列があると仮定したgrepは失敗した。基準の3.6.5にも文字列がないことを確認し、上記のELF依存・source版・hashで照合した。
- 最初の測定集計は設定差をoverrideの1行だけと仮定して停止した。実際の差である外部treeのdirty表示も記録し、それ以外の設定とkernel設定を照合した。
- SBOMのproject versionに短いSHAを渡す試行は検査器に拒否された。先行調査の基準とbuild基準の取り違えも訂正し、build基準の40桁SHAで生成し直した。
- CVE検査の初回とUID指定の再試行は出力permissionで失敗した。rootless Dockerではcontainerのrootが実行ユーザーに対応することを確認し、wrapperと同じuser 0:0で実行した。
- configureで任意の機能・文書toolがない警告や、e2fsprogsの文書生成のignored errorが出た。両側の通常buildは終了値0で完了した。

## 限界

QEMUの成功は、LCD、keyboard、I2C、firmware tryboot、実機での暗号性能・電源断の確認ではない。計画packageのTLS/SAE/EAP、全provider/algorithm、4系互換性は試験していない。3.5.9採用は11月10日のadvisoryが修正済みという意味ではない。

# S2 IMX219 カメラの最小構成

- 状態: 完了（tier A 採用、実機未確認）
- 日付: 2026-10-19
- 担当: Devin
- 関連: S2 カメラ対応、[起動・カーネル調査](../research/boot-and-kernel.md)、[生データ CSV](2026-10-19-s02-camera.csv)

## 目的と仮説

CM0 で IMX219 の V4L2 raw capture に必要な Unicam と sensor driver を module として有効にします。libcamera、VCHIQ、`bcm2835-isp` は対象外とし、cut-down firmware と GPU メモリー設定を変えません。camera/V4L2 module を必要最小限にすれば、Image の増加と QEMU 相対 ready-marker 時間を採否基準内に抑えられると仮定しました。

## 採否の基準（結果を見る前に書く）

- kernel `Image` の差分: **+65,536 B 以下**
- QEMU 相対 ready-marker の中央値の差分: **+1.0% 以下**
- 生成した module payload がすべて署名済みであること
- 当初の「`drivers/media/` 以下の全 module が allowlist と一致する」という基準文は、既存 CEC/RC module 15 個を考慮しておらず誤り。S2 の追加分だけを評価し、追加 module が次の camera/V4L2 core 12 個と一致すること: `bcm2835-unicam`、`imx219`、`mc`、`v4l2-async`、`v4l2-cci`、`v4l2-dv-timings`、`v4l2-fwnode`、`videobuf2-common`、`videobuf2-dma-contig`、`videobuf2-memops`、`videobuf2-v4l2`、`videodev`

## 手順

`BASE_WORKTREE` は基準 commit の checkout、`REPO` は S2 branch の checkout、`OUTPUT_DIR` は Buildroot の `O=` directory、`LOG_DIR` はリポジトリ外のログ保存先です。Buildroot の make は `env -u BASH_ENV` で実行しました。

```sh
BASE_WORKTREE=<基準 commit の checkout>
REPO=<devin/s2-camera の checkout>
REUSABLE_OUTPUT_DIR=<既存 Buildroot output>
BASE_OUTPUT_DIR=<base 用に複製した Buildroot output>
OUTPUT_DIR=<Buildroot の O= directory>
LOG_DIR=<リポジトリ外のログ directory>
BASE_BINARIES_DIR="$BASE_OUTPUT_DIR/images"
HOST_DIR="$OUTPUT_DIR/host"
BINARIES_DIR="$OUTPUT_DIR/images"

cp -a "$REUSABLE_OUTPUT_DIR" "$BASE_OUTPUT_DIR"
mkdir -p "$LOG_DIR/base/images"
env -u BASH_ENV make -C "$BASE_WORKTREE/vendor/buildroot" \
  BR2_EXTERNAL="$BASE_WORKTREE" O="$BASE_OUTPUT_DIR" msd_cardputerzero_defconfig
env -u BASH_ENV make -C "$BASE_OUTPUT_DIR" -j2
cp "$BASE_BINARIES_DIR/Image" "$LOG_DIR/base/images/"
cp "$BASE_BINARIES_DIR/sdcard.img" "$LOG_DIR/base/images/"

env -u BASH_ENV make -C "$REPO/vendor/buildroot" \
  BR2_EXTERNAL="$REPO" O="$OUTPUT_DIR" msd_cardputerzero_defconfig
env -u BASH_ENV make -C "$OUTPUT_DIR" linux-reconfigure
env -u BASH_ENV make -C "$OUTPUT_DIR" -j2
env -u BASH_ENV make -C "$OUTPUT_DIR" rpi-firmware-rebuild
env -u BASH_ENV make -C "$OUTPUT_DIR" target-post-image

"$REPO/board/cardputerzero/tools/check-kernel-fragment.sh" \
  "$REPO/board/cardputerzero/linux.fragment" "$OUTPUT_DIR/build/linux-custom/.config"
"$REPO/board/cardputerzero/tools/check-modules-dep.sh" "$OUTPUT_DIR/target"
"$REPO/board/cardputerzero/tools/check-dt-overlays.sh" \
  "$HOST_DIR" "$BINARIES_DIR" "$BINARIES_DIR/rpi-firmware/config.txt"

QEMU_MODULE_TEST= QEMU_ICOUNT=shift=0 "$REPO/board/cardputerzero/tools/bench/run-s6-boot-cost.sh" \
  s2-camera "$BINARIES_DIR/sdcard.img" "$BINARIES_DIR/Image" \
  "$BINARIES_DIR/bcm2710-rpi-3-b.dtb" "$LOG_DIR/variant/timing-controlled" \
  "$LOG_DIR/variant/boot-cost-controlled.csv"
```

試行1の base image は保持されていません。統制再測定では `a534690` を別 worktree / `O=` で再ビルドし、base の `Image=26,380,800 B` と `sdcard.img=771,751,936 B` を使いました。boot runner は `QEMU_ICOUNT=shift=0` と `QEMU_EXTRA_APPEND='initcall_debug printk.time=1 msd.sweep=1'` を設定します。測定時は `QEMU_MODULE_TEST=` を明示し、base と variant のどちらにも `msd.module-test=` を渡しません。通常の QEMU smoke test では `test-qemu.sh` の既定値 `usbnet,bcm2835-unicam,imx219` を使い、3 module すべての成功 marker を確認します。

artifact の byte 数は `stat` と `gzip -9n Image` で計測しました。boot VFAT の `kernel8.img` は Buildroot host の `mcopy` で抽出しています。host tool の版は `"$HOST_DIR/sbin/mke2fs" -V`、`"$HOST_DIR/bin/mksquashfs" -version`、`"$HOST_DIR/bin/genimage" --version`、`"$HOST_DIR/bin/dtc" --version` の出力から記録しました。

## 計測器の検証

QEMU p5/p6 serial log は `usbnet`、`bcm2835-unicam`、`imx219` の `modprobe` と `lsmod` が成功し、`MSD/Linux ready` に達したことを示します。guest 側 module-check hook が要求した module load を実行し、target module payload 1,051 個すべてに signature marker があることも確認しました。

ready-marker の timestamp は各 serial log と CSV で一致しました。base の run 間 spread は 0.005653 s、variant は 0.009828 s です。3 回としたのは `shift=0` icount を用いる S6 と同じ決定的な仮想時間比較の条件に合わせたためです。ただし今回の中央値差 0.001630 s は観測 spread より小さいため、わずかな差の実時間上の有意性は主張しません。採否は事前登録した中央値の +1.0% 閾値だけで判定します。

`libv4l-utils` は要求した `v4l2-ctl` / `media-ctl` だけでなく CEC・IR・compliance 等の utility と RC keymap も target に追加します。表にまとめた per-file diff 全件は `$LOG_DIR/variant/controlled-target-diff-clean.csv` にあります。

post-image の DT checker は `config.txt` の overlay を記載順に適用し、`sony,imx219` node（`/soc/i2c0mux/i2c@1/imx219@10`）と CSI1 の `okay` を確認しました。一時的に `dtoverlay=does-not-exist` を追加した試験では missing-overlay error で失敗し、`dtoverlay=imx219` をコメントアウトした試験では IMX219 assertion が実行されず成功しました。`rpi-firmware-rebuild` 後の package config は board config と一致し、`post-image.sh` は `${BINARIES_DIR}/rpi-firmware/config.txt` を checker に渡します。

カメラ電源の配線は、C154 V0.6.1 の回路図 p.10 で CAM_3V3 の LDO U36 (SSP7615-33DFR) の EN が R190 100 kΩ を介して VSYS_5V に pull-up され、R192 は未実装であることから、GPIO で切り替える設計ではありません。カメラコネクタ JP5 pin 17 と CM0 connector pin 44 は CAM_GPIO です。CM0 DTS は GPIO40 を `CAM_GPIO` と名付け、`cam1_reg` に `gpio = <&gpio 40 GPIO_ACTIVE_HIGH>` を設定します。標準 `imx219` overlay は cam1 を使うため、この GPIO を使用します。v5 の GPIO16 は `G16_PY32_RST` であり、v5 では追加の camera GPIO overlay を適用しません。したがって camera power GPIO の割当ては未解決事項ではなく、追加 GPIO hog も不要です。【一次】[C154 V0.6.1 schematic](https://m5stack-doc.oss-cn-shenzhen.aliyuncs.com/1243/C154-CardputerZERO_SCH_V0.6.1_20260702.pdf) p.5, p.10／[CM0 DTS](https://github.com/raspberrypi/linux/blob/234188315037848e5b07d65b85d38edc64095caa/arch/arm/boot/dts/broadcom/bcm2710-rpi-cm0.dts)／[M5 CardputerZero Makefile](https://github.com/m5stack/m5stack-linux-dtoverlays/blob/75518549a2640486f5d13ea72ca4935b198d7c20/modules/CardputerZero/Makefile)

## 捨てた試行と経緯

- trial 1 の boot time は base 側 `usbnet` のみ、variant 側 `usbnet,bcm2835-unicam,imx219` の module-test hook が ready marker 前に動作し、条件が一致しないため破棄しました。trial 1 の base image は保持されていません。再測定では `a534690` を別 worktree / `O=` で再ビルドし、両側で `QEMU_MODULE_TEST=` を設定しました。
- 再測定の確認中、再利用した variant `output/target` に S6 の一時 test artifact が残っていることが分かりました（`etc/init.d/S97msd-module-check`、`etc/init.d/S97msd-s6-hardening-check`、`etc/init.d/S97msd-z-hardening-check`、`usr/lib/msd-hardening/usbnet-unsigned.ko`）。`S97msd-z-hardening-check` は `msd.sweep=1` で ready marker 前に起動するため、これらを削除して production-only rootfs を再生成し、測定しました。
- `config.txt` の変更が再利用 O= の `rpi-firmware/config.txt` に反映されない試行がありました。`rpi-firmware-rebuild` 後に board config が正しくインストールされることを確認したため、`post-image.sh` の直接コピー workaround は採用せず、checker に package config のパスを渡します。config 変更後に O= を再利用するときは `rpi-firmware-rebuild` が必要です。
- 最初の media build では 36 個の media module ができ、無関係な sensor / video driver が含まれました。明示 disable を追加した後も UVC と Videobuf2 SG/VMALLOC が残り、原因は `USB_CONFIGFS_F_UVC` と `USB_G_WEBCAM` でした。両 parent を無効化して再構成し、最終 variant は 27 個（既存 RC/CEC 15 個と camera/core 12 個）になりました。
- 初回の QEMU 呼び出しでは `OUTPUT_DIR` を渡さず、既定位置に `sdcard.img` が見つからず起動前に失敗しました。再利用中の `O=` を明示して再実行しました。
- `mcopy` を PATH から呼ぶ方法は失敗しました。Buildroot host の `mcopy` を使って boot VFAT の kernel image を採取しました。
- host `kmod` は `-OPENSSL` build のため `modinfo -F signer` の signer field が空で、これだけでは未署名判定になりません。signature marker の全件 scan と QEMU module load を使って確認し直しました。
- Buildroot の post-build log には開発用 update-signing key を release に使わないよう警告があります。これは module signature の検査結果とは別の警告です。

## 結論

`Image` 差分 0 B、module payload の署名、修正した S2 追加 module allowlist、QEMU 相対 ready-marker 中央値差分 +0.0510% は基準内です。tier A を採用します。全 media module 集合に対する元の allowlist 文は既存 CEC/RC 15 個を考慮していなかったため、適合とは判定しません。rootfs 増加 +1,499,136 B は記録しますが、採否基準には含まれていないため、この判定を変えません。

QEMU は `raspi3b` / Pi 3B device tree を使用し、firmware overlay を適用していません。QEMU では GPIO、camera regulator、aux UART などの peripheral probe error と ioremap warning が記録される一方、両 slot は ready に達して三 module の load test に成功しました。boot-cost 用 serial logs には `msd.module-test=` と module-check marker がないことを確認しました。QEMU は CM0 camera pipeline や撮像の検証ではありません。**実機 capture は試していません。**

## 未確認の点

- 実機 `dmesg` での sensor ID 読み取り。
- 実機で `media-ctl -p` が示す topology と CSI1 2-lane raw capture。
- Lite 版で IMX219 probe が失敗する場合の実際の kernel message。

実機では `dmesg` の sensor ID、`media-ctl -p` の topology、CSI1 2-lane の `v4l2-ctl --stream-mmap` raw capture、Lite 版の probe-failure message を確認します。camera power routing は一次資料で確認済みです。
